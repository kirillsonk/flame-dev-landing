# Рабочий процесс Flame Dev

Редакция от 30 сентября 2026 года

## Текущая схема

GitHub является основным репозиторием для текущей работы и публикации

```text
github → https://github.com/kirillsonk/flame-dev-landing.git
```

- `dev` используется для текущих правок и проверки перед выпуском
- `main` связана с автоматическим развертыванием production на Timeweb
- Merge в `main` и push в `main` выполняем только по явному разрешению владельца после проверки результата
- Отправка изменений в `dev` не означает разрешения на выпуск в production
- Не используем force push, `push --mirror` и автоматический двусторонний merge

Имя `origin` в этом каталоге по-прежнему указывает на GitLab, поэтому в командах текущего процесса явно указываем `github`

## Перед началом работы

```bash
git status --short --branch
git fetch github --prune
```

При наличии незакоммиченных изменений сначала определяем их автора и назначение

Не сбрасываем и не перезаписываем изменения другого участника

Если рабочее дерево чистое и задача продолжается в общей ветке разработки

```bash
git switch dev
git pull --ff-only github dev
```

Если ветки разошлись, разбираем различия без force push

## Совместная работа с Claude

Последовательная работа может идти в одном каталоге с передачей статуса, ветки, коммита и незавершенных изменений между участниками

Для параллельной работы Codex и Claude используем отдельные worktree и ветки от актуальной `github/dev`

```bash
git fetch github
git worktree add ../flame-dev-claude -b claude/task-name github/dev
```

Новая worktree требует своей установки зависимостей

Не запускаем двух агентов на редактирование одних файлов в одном рабочем каталоге

Результат отдельной задачи сначала проверяем и объединяем с `dev`, затем готовим общий выпуск

## Локальный просмотр

Локальный режим предназначен для быстрых итераций на этом компьютере

```bash
npm run dev -- --hostname localhost --port 3101
```

Адрес для комментариев владельца — `http://localhost:3101/`

Перед запуском проверяем, не работает ли уже сервер на этом порту

Не останавливаем чужой процесс и не запускаем вторую сборку в том же каталоге `.next` одновременно с проверкой текущего сервера

В проекте есть серверные обработчики `/api/lead` и `/api/brief`, поэтому статическая выгрузка не заменяет полноценный запуск Next.js

## Проверка и передача результата

```bash
npm run check
git diff --check
git status --short
```

`check` последовательно выполняет сборку, ESLint и проверку TypeScript

Визуальные изменения проверяем в браузере на ширине 1440 и 390, мобильные изменения дополнительно на узких экранах и границах адаптивной сетки

Проверяем обе темы, навигацию между главной и кейсами, сенсорные сценарии, форму и режим уменьшенного движения

В передаче результата указываем состав изменений, результаты проверок, известные ограничения, ветку и ссылку на локальный просмотр

После проверки и коммита текущую ветку разработки отправляем в GitHub

```bash
git push -u github dev
```

Перед отправкой убеждаемся, что `dev` содержит только согласованные изменения этой итерации

## Выпуск в production

Рабочая последовательность — правки в `dev`, проверка, согласование владельцем, merge в `main`, автоматический деплой Timeweb

Перед merge сверяем состав изменений `dev` относительно актуальной `github/main`

Merge и push в `main` запускают выпуск, поэтому разрешение на обычные правки или отправку `dev` не подменяет отдельного разрешения на production

После разрешенного выпуска проверяем завершение сборки Timeweb, состояние приложения и основные пользовательские сценарии на production

Не сообщаем об успешном деплое только на основании успешного push

## Доставка заявок

- Сервер сообщает об успехе только после подтверждения доставки в Telegram
- На Timeweb серверные запросы могут идти через настроенный ретранслятор, локально возможна прямая работа по ключам
- Без необходимой конфигурации отправка возвращает 503
- При ошибке или тайм-ауте доставки возвращается 502, введенные данные сохраняются в форме
- Секреты, контакты посетителя и содержимое заявки не записываются в журнал ошибки и не добавляются в Git
- Подключение реального получателя и контрольную отправку согласуем отдельно
- Визуальный просмотр формы не считается проверкой доставки заявки

## Историческая схема

До перехода на текущий процесс основным репозиторием был GitLab

```text
origin → git@gitlab.com:flame-dev/flame-dev-landing.git
```

Работа велась в `codex/workflow-and-site-audit`, GitHub использовался как копия истории, а публикация предпросмотра выполнялась через Sites

Конфигурации GitLab CI, адаптер `build:sites`, `.openai/hosting.json` и описание в `doc/ITERATION_2026-09-28.md` относятся к той схеме

Их наличие не означает, что нужно отправлять текущие правки в GitLab, публиковать Sites или подключать Railway

Ретранслятор `flamedev-relay` (папка `relay/`, Timeweb nl-1) собирается без автодеплоя с 1 октября 2026: после изменений в `relay/` деплой запускается вручную в панели Timeweb. Сайт `flamedev-site` по-прежнему выкатывается автоматически из `main`
