# Рабочий процесс Flame Dev

Редакция от 25 сентября 2026 года

## История проекта

Основной remote `origin` указывает на GitLab

```text
git@gitlab.com:flame-dev/flame-dev-landing.git
```

GitHub подключается отдельным remote `github` к репозиторию с той же историей коммитов

Не используем два независимых проекта, автоматический двусторонний merge или `push --mirror`

При подключении второй площадки отправляем туда текущую историю и нужные ветки, не создаем новую историю через загрузку файлов

## Статус настройки

- Чтение GitLab по SSH проверено
- Настройки pull.ff=only, fetch.prune=true и push.default=simple заданы локально
- Изменения этой итерации ведутся в `codex/workflow-and-site-audit`
- Конфигурации проверок GitLab и GitHub добавлены
- Репозиторий GitHub создан владельцем по адресу `https://github.com/kirillsonk/flame-dev-landing`
- Проверка отправки в GitHub через HTTPS без загрузки кода прошла успешно
- Отправка истории ожидает уточнения публичности репозитория
- Railway не используем для этой рабочей версии по решению владельца
- Публикация через Sites пока не выполнена, локальные файлы инструкций установленного плагина отсутствуют

## Перед началом работы

```bash
git status --short --branch
git fetch origin --prune
```

При наличии незакоммиченных изменений сначала определить их автора и назначение

Не сбрасывать и не перезаписывать изменения другого участника

Для новой задачи создавать отдельную ветку от актуальной основной ветки

```bash
git switch main
git pull --ff-only origin main
git switch -c codex/task-name
```

## Совместная работа с Claude

Последовательная работа может идти в одном каталоге с передачей статуса и коммита между участниками

Для параллельной работы используем отдельные worktree и ветки

Пример для новой независимой задачи Claude

```bash
git fetch origin
git worktree add ../flame-dev-claude -b claude/task-name origin/main
```

Новая worktree требует своей установки зависимостей

Не запускаем двух агентов на редактирование одних файлов в одном рабочем каталоге

## Проверка и передача результата

```bash
npm run check
git diff --check
git status --short
```

Визуальные изменения дополнительно проверяем в браузере на ширине 1440 и 390

В описании результата указываем состав изменений, проверку, риски и ссылку на предпросмотр

Отправляем рабочую ветку и создаем merge request в GitLab

```bash
git push -u origin HEAD
```

Изменения из GitHub PR сначала попадают в рабочую ветку основного локального репозитория, проходят проверку и merge request в GitLab

После принятия изменений обновляем копию основной ветки на GitHub

```bash
git switch main
git pull --ff-only origin main
git push github main
```

Если ветки разошлись, прекращаем синхронизацию и разбираем различия без force push

## Предпросмотр

Локальный режим предназначен для быстрых итераций на этом компьютере

```bash
npm run dev -- --hostname 127.0.0.1 --port 3100
```

Для внешней ссылки используем Sites на домене ChatGPT по решению владельца

Перед первой публикацией восстановить инструкции Sites и проверить поддержку серверной части Next.js

В проекте есть серверный POST `/api/lead`, поэтому обычная статическая выгрузка не заменяет полноценное развертывание

Нельзя выдавать визуальный предпросмотр без работающей доставки за полностью работающий сайт

При подключении Sites сохранить его идентификатор и воспроизводимую инструкцию публикации в проекте

До подключения внешнего хостинга проверяем изменения локально

## Доставка заявок

- Сервер сообщает об успехе только после подтверждения Telegram
- Без конфигурации возвращается 503
- При ошибке или тайм-ауте доставки возвращается 502
- Контакты посетителя и токен не записываются в журнал ошибки
- Подключение реального получателя и контрольную отправку подтверждаем отдельно

## Ближайшие незавершенные подключения

- Отправка и проверка одинакового коммита основной ветки на двух площадках
- Восстановление доступности инструкций Sites
- Публикация и проверка внешней ссылки
- Проверка прав запуска GitLab CI и результата серверной проверки
